# 1.16.0 — fan-out performance round

**Status:** implemented, measured, shipped as a local global-tool build. **Date:** 2026-10-16.

> This file sits in `docs/` because that is where it was asked for. Earlier release plans live in
> [`docs/history/`](history/README.md) (`<version>_<subject>.md`); move it there when 1.17.0 lands.

A clean-up and performance round on top of 1.15.0 (`ed771d8`, see
[`history/1_15_0_plan.md`](history/1_15_0_plan.md)). No rule was added or retuned. The goal
was wall time on the reference monorepo (MILKRUN, about 1,900 C# documents across about 120
projects), where the analyser fan-out had become the whole cost of a run.

## Headline

1.15.0 compared with 1.16.0. Each binary was built Release from `git archive`, and the two ran in
4 alternating rounds on one machine (Ryzen 7 8840U, 8 cores/16 threads). Every report was
byte-identical to the 1.15.0 reference.

| Target | Metric | 1.15.0 (mean) | 1.16.0 (median) | Change |
| --- | --- | --- | --- | --- |
| MILKRUN `--duplicate-detection` | Wall | 118.0 s | 63.1 s | −47% |
| | Analysis stage | 98.1 s | 44.1 s | −55% |
| | Package analysers (SNP0003/0004/0012/0013) | 80.9 s | 19.4 s | −76% |
| | Peak working set | ~2.14 GB | ~2.23 GB | +4% |
| Snipper.slnx (self-scan) | Wall | 9.05 s | 6.8 s | −25% |
| | Analysis stage | 6.7 s | 4.35 s | −35% |
| | Peak working set | ~385 MB | ~483 MB | +~100 MB |

The 1.16.0 MILKRUN column uses the median because one of its four rounds was a 97.5 s outlier: the
same build ran at 57.7, 60.6 and 65.5 s. The mean including that outlier is 70.3 s wall. MILKRUN
noise is about ±25 s between identical runs, so treat one run as anecdote.

## Why server GC was the big one

The csproj comment said server GC was "neutral-to-worse". That was true on the small targets it had
been measured on. On MILKRUN the fan-out is **GC-bound**:

- Under workstation GC, SNP0005/6's reference phase spent 34–41% of its wall time in GC pauses
  (~2,400–3,100 gen0 collections).
- The process averaged only ~7.5 of 16 logical cores, whether SNP0005/6 ran alone or with every
  other analyser.
- `FindReferencesAsync` allocates heavily and runs 16 wide. Each workstation gen0 collection
  suspends all 16 threads.

Two earlier conclusions were drawn under workstation GC, and both should be read in that light:
- Parallel SNP0019 made the run slower.
- The shared `ReferenceSearch` was neutral.

**Measure `GC.GetTotalPauseDuration()` before calling a Snipper run CPU-bound.**

## Tried and dropped

| Experiment | Result | Why dropped |
| --- | --- | --- |
| Parallel SNP0019 (unused-using) per document | 98 → 114 s analysis (worse) | Measured under workstation GC, so GC pressure is the likely cause. Not re-measured under server GC. |
| Run the DI registration scan concurrently with the fan-out | Neutral under server GC | The CPU is already busy in that window. Reverted. |

## Behaviour changes

| Change | Baseline effect |
| --- | --- |
| Console rows within a file are sorted by line. | None. JSON/SARIF are byte-identical. |
| Namespace exclusion runs on findings after analysis. A clone set (SNP0031/32) is kept or excluded by its **anchor**, and the kept finding names **every** copy, including copies in excluded namespaces. Nested namespaces resolve to their declared `A.B`. The suppression audit has one row per namespace. A finding hidden by both a disabled rule and a namespace exclusion is credited to the disabled rule. | **Re-baseline if you use `--exclude-namespaces` with `--duplicate-detection`.** Messages of clone sets that touched an excluded namespace now list every copy. On MILKRUN, 61 sets were previously trimmed. Without namespace exclusions, nothing changes. |
| No false "working tree is dirty" warning after `--baseline` rewrites the baseline. | None. |
| Server GC is on. | None. Peak memory rises by about 100 MB on small solutions and about 4% on MILKRUN. **`DOTNET_gcServer=0` turns it off** on a memory-constrained agent. |

## Remaining critical path

After `48feea3`, the package analysers finish at about 19 s after the fan-out starts. The tail is now
**SNP0005/6** (~25 s, reference searches already early-exiting) and **UnusedUsing / SNP0019** (~25 s).
The next round should re-measure parallel SNP0019 under server GC before trying anything else.

## Verification

- 755 tests pass. Formatting: `dotnet format whitespace --verify-no-changes` is clean.
- MILKRUN reports are byte-identical to the 1.15.0 reference in 8 of 8 A/B runs. Self-scan reports
  are identical between 1.15.0 and 1.16.0.
- **The self-analysis CI gate does not pass against the committed `snipper-baseline.json`.** That
  baseline was last refreshed before 1.15.0. Complexity scores of Snipper's own analysers moved in
  the refactors above (SNP0033 +12, SNP0034 +19). SNP0006 reports all seven
  `IFindReferencesProgress` members of the new `FirstReferenceProgress` as unused, and one SNP0003 entry is new. The baseline
  needs a refresh before this branch passes CI. See the note on SNP0006 below.
- **Possible SNP0006 false positive.** Members implementing an *external* interface
  (`Microsoft.CodeAnalysis.FindSymbols.IFindReferencesProgress`) on a private nested class are
  reported as unused. Roslyn calls them through the interface. Worth a test and a fix in 1.16.x.
