# 1.12.0 - F5: SNP0032 marker precision

**Status:** implemented, measured, released.
**Rule changed:** SNP0032 (clone-set fix drift) - tier only. **No finding is removed or added.**
**Measurement:** 4,166 findings before and after on the reference monorepo; SNP0032 204 both
sides; **High 22 -> 9, Advisory 182 -> 195. Zero new findings, every other rule byte-identical.**

---

## 1. What the backlog said, and what was true

F5 was filed in 1.7.1 as ~17 SNP0032 `High` findings promoted by
`DefensiveFixMarkers.IsFixShaped`, which matched bare words (`null`, `Length`, `Count`, `try`)
against raw added patch text. The proposed fix was three parts: reject comment lines in
`CarriesCode`, require a *shape* rather than a bare word, and reject relocated hunks with a
whole-hunk `IsRelocation` check.

**The diagnosis held. The count did not: 22 High, not ~17.** Same lesson as F2, whose 1.7.1 size
estimate of "70% of SNP0006" turned out to be 5.4%.

**The proposed fix, implemented as written, would have been wrong in three ways.** Each was found
by reading the actual patches before changing any code:

| Proposed | Why it fails | What shipped instead |
| --- | --- | --- |
| Whole-hunk `IsRelocation`: `added.All(l => removed.Any(r => r.TrimStart() == l.TrimStart()))` | The headline case is `if (checkpoint != null) return checkpoint;` **split across two lines**. One removed line, two added lines - no added line equals the removed one, so the check reports *not* relocated and the reformat stays High. | Per-line **containment**: an added line whose trimmed text is already contained in (or already contains) a removed line is a rearrangement, not a contribution. Catches the split, catches the re-indent, and still lets a hunk that reformats *and* fixes report the real fix. |
| Shape list `is null`, `?? throw`, `?.`, `ThrowIfNull` | Omits `!= null` and `== null`, **the commonest null guards in C#**. `PaymentExtensions.cs`'s genuine one-sided fix would have been demoted to Advisory. | `== null`, `!= null`, `is null`, `is not null`, `?.`, `??` - all six. |
| Drop bare `Length`/`Count` | `if (list.Count > 0)` **is** a bounds guard and was always reported as one. Dropping the word demotes real checks. | The name is kept but must be **followed by a comparison operator**. `list.Count > 0` is a guard; `public int Count { get; set; }`, `actualLineItems.Count.Should().Be(1)` and `Name = "…-requests.count"` are not. |

## 2. What was actually wrong, measured per case

All 22 High findings were traced to their commits and the added lines extracted by hand. The
matcher fired on these, none of which is a guard:

| Observed added line | Why it is not a fix | Shipped as |
| --- | --- | --- |
| `string? successRedirectUrl = null;` | an initialiser, not a comparison | `null` dropped as a bare word |
| `public int Count { get; set; }` | a property declaration | bounds name needs a following comparison |
| `actualLineItems.Count.Should().Be(1);` | a test assertion | same |
| `[Counter<int>(..., Name = "…-requests.count")]` | a metric name, inside a string | literals stripped before matching |
| `/// Fills the tag; null = tag omitted` | prose | comments stripped |
| `Deserialize<CacheDataEntry>("{…\"priceFamilyId\":null…}")` | a 1.5 KB JSON fixture | literals stripped |
| `public static bool IsNullOrEmpty<T>(…)` | **the marker matched its own method name** | guard calls need the `(` immediately after the name |
| `if (checkpoint != null)` (split from a removed one-liner) | a reformat | per-line pre-existence |
| `MaximumWaitTime = … : null` (re-indented) | a relocation | same |
| `[InlineData(…, null, …)]` | test data | `null` dropped as a bare word |

Two more that the 1.7.1 note did not call out:

- **`throw`/`try`/`catch` anywhere in the line.** Now anchored to statement position, so
  `trying` and a test name containing `try` cannot fire it.
- **`CarriesCode` was checking the wrong text.** It asked whether a line contains a letter, and a
  doc comment does. Stripping comments and literals first means the code check runs on code.

## 3. Verification found two defects in the first implementation

The A/B was run against the reference monorepo *before* the release, and the prediction of which
findings survive did not match. Both differences were real, and both are now regression tests.

**`ProductTypeFactory.cs` - demoted, and correctly so.** Predicted High. The hunk is **232 added
lines against 233 removed** - a wholesale restructure - and all four of its guard lines appear
verbatim on the removed side. A relocation, which is what the rule exists to reject.

**`UpdateCustomerRequest.cs` - wrongly demoted.** Predicted High, came out Advisory. The line is

```csharp
=> !string.IsNullOrWhiteSpace(DateOfBirth) ? DateOnly.Parse(DateOfBirth) : null;
```

and the consuming-position test required a token to *immediately* precede the call. Here a
negation and a member access sit between the arrow and the call, so the guard went unseen. Fixed
by allowing a leading `=>` or `return` anywhere before the call - and deliberately *not* `?` or
`:`, which would promote every nullable property initialised in a constructor. Both halves have
tests.

The 1.7.1 investigator had already called this one "a genuine inconsistency worth fixing": one copy
of a request DTO hardened `DateOnly? DateOfBirth` to `string?` with a parse-and-validate, and the
sibling still declares `DateOnly?`.

## 4. What did not change

**No finding was removed.** A tier demotion keeps the finding, the commit, the sibling list and the
catch-up clause; what changes is that it is no longer asserting a defect. 204 SNP0032 findings
before, 204 after.

The nine survivors were each checked against their patch and are genuine one-sided guards:
`PaymentExtensions` (`!= null`), `CustomTypesSetupTask`, `ProductTypeFactory` (survives on a
different hunk), `GetCategoriesQuery`, `UpdateCustomerRequest`, `CustomerEventJsonConverter`,
`MilkrunStoreExtensions`, `AnalyticsEventMessageHandler`, `TaxInvoiceSenderService`.

**Two surviving High findings are still not right**, for a reason outside SNP0032: `IOrderApi.cs`
is paired with `NashJob.cs` and `UpdateCustomerRequest.cs` with `BloomreachImageSetData.cs` -
unrelated types matched by the clone detector. That is a shape collision in the set.

> territory, and it is recorded there rather than papered over here."* **F6 shipped in
> 1.13.0 and did not cover it.** F6's scope was SNP0003 (unloaded consumer projects), SNP0024
> (primary-constructor captures), SNP0031 fingerprint identity, and the DI false alarm - the
> SNP0031 identity item fixed two findings *sharing* one fingerprint, which is the opposite
> problem from two findings wrongly *sharing a clone set*. Routing this here was a wrong
> turn recorded as a right one.
>
> **Both pairs still report High on the reference monorepo**, measured at 1.14.0 with
> `--duplicate-detection --clone-drift`:
>
> | Anchor | Paired with | Still High |

>
> The cause is now identifiable rather than merely named. Token normalisation erases
> identifiers, and a run of nullable auto-properties - `public string? Name { get; init; }` -
> normalises to one shape regardless of what it is a property of. `BloomreachOrder`,
> `NashJob` and `BloomreachImageSetData` are all bags of nullable properties, so they are
> token-identical without any of them having been copied from any other. It is the same
> mechanism already documented for `const` tables, applied to DTO property bags.
>
> **This is open, and closing it is a rule-semantics decision, not a bug fix** - see
> `docs/Snipper-Feature-Parity-Roadmap.md` for the live entry.
>
> **Calibrated 2026-10-12, after this note was written.** The sentence above said this could not be
> settled from two examples. It has since been settled - on all 1,131 SNP0031 sets, not a sample. A
> suppression guard was designed, measured and **rejected on evidence**: 65% of property-bag pairs
> share no property name at all, but the name-overlap discriminator that would remove them also
> suppresses `Metro60ExtendedProductAttributeDefinitions.cs` /
> `WoolworthsProductAttributeDefinitions.cs`, which is genuine per-brand schema duplication.
> Identifier-disjoint-and-still-duplicated is exactly the Type-2 rename clone SNP0031 exists to find,
> so this is a feature being traded for a quieter report, not a threshold to tune.
>
> The class is also **larger than the two High findings that exposed it**: 52.7% of all SNP0031 sets
> are declaration-only (17.1% const tables, 15.3% DTO property bags, 20.3% other declarations), and
> 47.3% contain a method body. The surviving candidate is a **tier change in 4C** - withhold the
> "an equivalent change reached the sibling later" claim for declaration-only identifier-disjoint
> sets - rather than a tightening of SNP0031, which is behaving exactly as documented.

## 6. Migration

**A 1.11.0 baseline will report 13 new findings.** `BaselineService.ComputeFingerprint` hashes
`RuleId | relativePath | Message`, and the tier is the first words of the message - a demoted
finding reads `One-sided change` or `One-sided rename` where it read `One-sided defensive fix`. So
each of the 13 re-fingerprints and surfaces as new against the old baseline.

That is the correct signal: the finding's *content* changed, and a baseline that silently carried
it forward would be hiding a reclassification. Re-baseline, as for 1.11.0.

No finding disappears, so nothing needs removing from a baseline by hand - the 13 new entries
replace 13 old ones.
