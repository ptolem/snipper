# 1.13.0 — F6: three evidence channels and one identity fix

**Status: implemented, measured, released.**

F6 was the last row of the 1.7.1 false-positive backlog. It arrived as "four remaining
single-finding classes, each needing its own evidence channel" — a description that
turned out to be wrong in three ways. The count was 1 per class; one class was already
fixed; and one of the prescribed fixes would have deleted true positives.

The backlog's *mechanisms* survived contact with the code. All three live classes were
real, and all three turned out to be instances of the pattern the backlog itself named:
**a rule has no channel for the evidence it needs, so it asserts something it cannot
support.**

## 2. (a) SNP0003 — an unanalysable consumer is not an absent consumer

`UnreferencedPackageAnalyser` builds `consumersClosure` from **loaded** projects, then
asserts:

> Package 'X' contributes assemblies but no symbol from it is used in project 'Y' **or
> its consumers**.

A `.csproj` on disk that the workspace never opened is a real consumer. It has no
compilation, so no symbol usage can be read from it — but its existence means the
sentence above is an **assumption, not a measurement**.

Suppressing the finding would have hidden a real candidate. The fix is to make the tier
tell the truth:

```
Package 'X' contributes assemblies but no symbol from it is used in project 'Y' or its
loaded consumers. Unloaded project(s) outside the solution may still use it:
M60.BridgingServices.ProductsUp.WebHost.
```

**High → Moderate, and the finding names what to check.** The reader gets a next action
rather than only a lower number.

Two details that a simpler version would get wrong:

- **`PrivateAssets=all` is exempt.** Nothing flows to any consumer, loaded or not, so
  consumer usage — including an unloaded consumer's — is irrelevant. A reference marked
  it keeps High. (The negative-control test caught the over-broad first version, which
  capped everything declared by an affected project.)
- **The walk is transitive and honours the same flow rules** as the loaded closure: an
  edge marked `PrivateAssets=all` stops propagation past that project.

`DetachedProjectScanner.ResolveRootDirectory` moved out of `OrphanProjectAnalyser` so
both analysers resolve the sweep root the same way. A sweep from an arbitrary root would
walk an unbounded filesystem, so it returns null when no single root contains every
project.

**Measured:** 7 of 16 SNP0003 findings capped, each naming the unloaded project.

## 3. (b) SNP0024 — a captured parameter is instance state

`TryEvaluateCanBeStaticAsync` proves a method touches no instance state by resolving
every name in the body and rejecting anything that binds to a member of the containing
hierarchy. The check covered fields, properties, methods and events.

A primary-constructor parameter read inside an instance method is captured state — the
compiler synthesises a field for it — but `GetSymbolInfo` binds the name to an
**`IParameterSymbol` owned by the type's constructor**, which is none of those four. The
walk found nothing, and the method was proposed `static` when making it `static` would
not compile.

```csharp
if (symbol is IParameterSymbol { ContainingSymbol: IMethodSymbol { MethodKind: MethodKind.Constructor } capturedBy }
    && IsInHierarchy(capturedBy.ContainingType, method.ContainingType))
{
    return null;
}
```

Only a **constructor-owned** parameter counts. The method's own parameters are
parameters too, and a method using only those is genuinely static — `ParamsOnly` in the
fixture is the negative control that keeps this from silencing a whole class.

**Measured: SNP0024 701 → 419.** The backlog reported 1 finding; the class of defect was
**282**. All 282 were verified against source — sampled across the range, including cases
whose bodies reference `featureFlags`/`timeProvider` and `customerCommandsPublisher` on
lines well past the method signature. Every one is a method that genuinely cannot be
made static.

## 4. (c) SNP0031 — identity, not suppression

The backlog's prescription was *"dedupe by `(rule, file, span)` and emit a column/span
field"*. Applying it would have been a **regression**: the colliding findings at
`MyProfile/WebApplicationBuilderExtensions.cs:109` are two different, real clone sets
(siblings `Rewards.API:58` and `CommerceTools.Products:154`). Merging them loses a clone.

The real defect was one layer down, and it is not specific to SNP0031:

```
fingerprint = SHA256(RuleId | relativePath | Message)
```

**The fingerprint carries no line number.** Two findings in the same file rendering the
same message therefore hash to one value — so suppressing one silently suppresses the
other, and neither is distinguishable from its neighbour in a report.

Measured on the reference monorepo before the fix: **205 of 4,166 findings shared a
fingerprint with another finding.** For SNP0031, 8 of 1,094 sets were affected. Every
other rule in the table below was untouched, because most messages already name the
symbol that distinguishes them.

The fix is what `CloneDriftClassifier.DescribeSiblings` already does for SNP0032 — name
the copies:

```
125-token block (15 lines) duplicated 2 time(s) across 2 file(s). Duplicated in:
src/Metro60.Rewards.API/WebApplicationBuilderExtensions.cs:58, ...
```

**SNP0031 count unchanged at 1,094; colliding fingerprints 8 → 0.** Every one of those
1,094 messages changes, so all of them re-fingerprint — which is why 1.13.0 requires a
re-baseline for a release that *removes* findings and *adds* none.

A second, smaller instance of the same defect was fixed on the write side:
`BaselineService.Write` now de-duplicates. Writing the same fingerprint twice grew the
file on every run and implied two suppressed findings where there is one.

## 6. What this release costs a consumer

**Re-baseline required.** Not because counts moved alone:

- 1,094 SNP0031 findings change message, so all re-fingerprint.
- 282 SNP0024 findings disappear and are recorded as resolved.
- 7 SNP0003 findings change tier and message.

A consumer reading only the finding count would see 3,962 → 3,680 and conclude the tool
got quieter. It got *more* accurate: no finding was removed that was not a false
positive, and every finding that survives can now be told apart from its neighbours.
