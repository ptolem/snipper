# 1.14.0 — SNP0034, cognitive complexity

**Status:** implemented, measured, shipped. **Date:** 2026-10-11.

The item the 1.10.0 research note added "at the owner's request" and explicitly left unimplemented.
Two questions were left open for whoever picked it up. Both are answered here with measurements
rather than assertions.

## What shipped

`CognitiveComplexityAnalyser` (SNP0034, Advisory, `Complexity` category), on by default, plus
`--max-cognitive-complexity`.

This is SonarSource's cognitive complexity (spec 1.2), not a re-spelling of cyclomatic. The rule is
that a method's score is `1 + nesting` for each break in linear flow, plus `1` for each break
*nested inside another break*. That last term is the whole reason it is a separate rule ID: SNP0033
counts decision points with a depth-agnostic `DescendantNodes` walk, so it cannot distinguish "six
flat branches" from "one branch wrapping five others". Cognitive complexity is built to.

Three constructs require a traversal cyclomatic does not use — a nesting level carried through a
recursive descent, pre-order flattening of boolean chains, and function-like scopes that nest
without incrementing — so this replaced the walk rather than extending it.

## Open question 1: threshold, measured rather than copied

The note said: *"calibrate the threshold on the reference monorepo rather than copying SonarQube's
15 — the 1.7.1 tuning no-go is a standing reminder that Snipper's codebase rewards different
numbers."*

**The default is 15, and the reason it stayed is that the measurement supported it.**

Running at a threshold of 1 exposes the whole distribution rather than the tail:

| Cognitive score | Methods | Cumulative above threshold |
| --- | --- | --- |
| 2–10 | ~1,100 | >10: 176 · >12: 123 · >14: 90 |
| 11–15 | ~110 | **>15: 80** |
| 16–20 | ~31 | >18: 60 · >20: 49 |
| 21+ | ~20 | >25: 27 · >30: 14 |

The obvious move was to raise the ceiling until SNP0034's count matched SNP0033's 42, which lands at
20. **That was rejected on evidence**: reading the methods at the boundary showed the 15–20 band is
not padding. `CartItemMappings.GetSubstitution` (16) is a four-deep nested ternary chain over
substitution preferences; `StoresController.ImportStores` (16) guards, loops and branches
interleaved. Those are real, and raising the threshold to hit an arbitrary count target would delete
them — which is exactly the shape of the 1.7.1 no-go, in reverse.

So 15 ships. It is also the number two independent implementations use (SonarQube S3776, PMD), which
is worth something when our own measurement agrees rather than contradicts.

## Open question 2: suppress one, or report both?

**Both are reported. Neither suppresses the other.** At the defaults, on the reference monorepo:

| | Methods |
| --- | --- |
| Breach both SNP0033 and SNP0034 | 29 |
| **SNP0034 only** | **51** |
| SNP0033 only | 13 |

The 51 are the reason. Two thirds of what SNP0034 reports, SNP0033 does not — that is the gap the
rule exists to close, and suppressing it would delete the rule's entire reason for existing. The 13
cyclomatic-only methods are equally real: a method with six flat guards and no nesting scores the
same under both, so cognitive has nothing to add.

The message names the sibling rule so the disagreement is never a surprise:

> Cognitive complexity 18 exceeds the maximum of 15. Nesting is weighted more heavily than branch
> count, so a method can breach this while passing SNP0033.

Consumers who want one metric turn the other off by ID in `snipper.json`. Raising a threshold to
approximate "only the other one" would be a worse approximation than the suppression it replaced.

## Deliberate divergences from the spec

Both are documented in the analyser's class summary and pinned by tests, because an unstated
difference from the reference is how a parity claim quietly stops being true.

1. **Recursion cycles are not counted.** The spec's +1 for "each method in a recursion cycle" needs a
   solution-wide call graph. clang-tidy declines it for the same reason. Snipper's complexity rules
   are purely syntactic so that they are deterministic and immune to restore state.
2. **Preprocessor conditionals are not counted.** clang-tidy documents the same omission. Charging
   `#if` would mean scoring disabled text and making the count depend on build configuration — the
   exact failure mode 1.7.5 was written about.

A third, smaller one: a `catch` filter is not charged separately. SonarSource charges it; a filtered
catch reads as one branch, and charging it twice makes the threshold arbitrary.

## A correction to the research note

The note recorded `a && b && c || d || e` as costing **+3**. It costs **2**.

The expression parses as `(a && b && c) || (d || e)`, so a pre-order walk over the logical operators
meets `||, ||, &&, &&` — two runs of like operators. The "+3" in the whitepaper's figure annotates
the enclosing `if` line: +1 for the `if`, +2 for the chain. Both numbers are now asserted separately
in `Mixed_Operators_Cost_One_Each_Time_They_Change`, which is the test to look at first if this
reading is ever disputed.

This is the third time a research-note number in this repository did not survive contact with the
code (after SNP0031's "dedupe by (rule, file, span)" in F6 and the per-set/normalisation sequencing
note in 1.10.0). The pattern is consistent enough to be worth stating: **an item's diagnosis is not
evidence.** Every one of the three was a plausible mechanism, and every one was refuted by a test
that took minutes to write.

## Post-release triage: what a full sweep actually found

The release gate sampled SNP0034's findings. Afterwards, all 80 were triaged rather than sampled,
and the other 2,384 findings in the report were looked at by certainty tier. Three results, two of
which changed the shipped behaviour.

### 1. No counting bugs, and one number that is easy to get wrong

Every score that was hand-checked matched the spec. One case is worth recording because it looks
like a bug and is not.

`StoreInventoryRepository.ReserveInventory` reports **cognitive 19 / cyclomatic 3**, and the lambda
inside it reports cyclomatic 6 on its own line. Read quickly, that looks like a 6x over-count. It
is not:

- **SNP0033 scores every callable body independently**, which is ReSharper's model. The lambda is
  its own unit, and the enclosing method is explicitly *not* charged for it.
- **SNP0034 scores a lambda inside its parent**, because the whitepaper counts a nested lambda as
  raising the nesting level without taking an increment of its own.

So the same construct is reported at two different numbers under two different metrics, and both are
correct. Hand-scoring the method gives exactly 19 — the lambda's +1 nesting level is what does it.

**The consequence is worth stating as a property of the rule**: a lambda adds +1 nesting to its
entire body, so `async`/callback-heavy code scores materially higher than the same logic written
without a lambda. That is spec-correct and matches SonarSource, but it means a high cognitive score
on a method full of lambdas is partly an artefact of the lambda, not of the branching.

### 2. The noise class is "long, not hard" — and it is arithmetic, not a bug

Comparing each finding's cognitive score to its cyclomatic score gives the nesting weight directly,
because cyclomatic ignores depth. Of the 80: 10 are deeply nested, 25 nested, 26 shallow, and **13
score roughly the same as cyclomatic**, meaning nesting added almost nothing.

Two of those were confirmed by reading the code:

| Finding | Shape |
| --- | --- |
| `Doubles.cs` (39) | ~39 sibling `if (param is not null)` blocks. A test fixture. |
| `ArticleEventMapper.cs` (31) | ~25 sibling `if (x != null) field = x;` guards. |

Both are arithmetically correct — there really are 39 branches — and neither is a defect worth
changing. There is no nesting, no interaction, and no reading order to hold in your head. Cognitive
complexity exists to separate *hard* from *long*, and a flat wall of independent guards is the one
shape where that distinction does not help, because nothing in the metric notices the guards are
independent.

This is the same behaviour as SonarSource's S3776 on builders and test factories. It is not a defect
in Snipper's implementation, so it was not "fixed" by changing the counting.

### 3. Test code is now excluded by default

Acting on the above: **both complexity rules skip test code by default.** A directory named exactly
`test` or `tests`, or a project whose final dotted segment is `Test`/`Tests` or ends with `Tests`.

The trigger was case 2 — the highest cognitive score in the entire report (39) was a test fixture of
the exact shape that shape-2 findings describe. A review trigger that fires on code nobody reviews
trains the reader to ignore the rule on the code they do care about.

The test is deliberately narrow and **never a substring match**, so production code called `Contest`,
`Testing` or `Latest` stays in scope. Silently dropping real code is a far worse failure than a
noisy finding, and a rule that quietly shrinks is harder to trust than one that complains.

**Measured effect on the reference monorepo: 2 findings** (SNP0033 and SNP0034 on `Doubles.cs`), and
no others — MILKRUN's test code is disciplined and breaches neither threshold anywhere else. That is
a small number, and it is reported as a small number: the change earns its place by removing the
single worst finding in the report and by protecting repositories whose fixtures are heavier, not by
clearing a queue on this one.

It is scoped to the complexity rules. A dead private member is just as dead in a test project, so
`ShouldSkipDocument` is untouched and the reference-checking rules keep reporting there.

### The rest of the report

The 266 **Guaranteed** findings were spot-checked and hold up:

- SNP0001 `GetAllProducts` is reported while eight other methods share that name in seven files —
  resolution is by symbol, not by name, and the flagged one is genuinely unreferenced.
- SNP0009 correctly reports only the unused half of a deconstruction
  (`var (customer, mobilePhoneNumber) = ...`), and correctly catches an unused `foreach` key.

One **message defect** was found and not fixed: SNP0009 labels a switch-arm *pattern variable*
(`List<object> set => new HashSet<T>()`) as a "Local variable". The finding is real and removable —
C# allows a type pattern with no designation — but the message names the wrong construct, and
correcting it is a separate change.

## Post-release: 4C no longer asserts a peer it cannot demonstrate

The calibration in `docs/Snipper-Feature-Parity-Roadmap.md` found that 52.7% of SNP0031's output
is declaration-only, and 65% of DTO property-bag pairs share **no identifier at all**. A
suppression guard in 1C was designed, measured, and rejected — it would also have removed genuine
Type-2 rename clones, which is the feature. The change shipped here is in **4C instead**, because
that is where the unsupported claim actually is.

`Classify` takes a fourth input, `comparable`. SNP0031 computes it per set, while it still holds the
syntax trees: a set is *incomparable* only when **every** member's region holds no executable
statement **and** no member shares a single identifier with the anchor. Both halves are required.
Either alone is too broad — identifier-disjointness alone would reject genuine Type-2 method clones,
declaration-onlyness alone would reject any two identically-shaped configuration classes.

The evidence is a second, parallel walk of each file recording identifier text by line and the lines
carrying a statement, arrow expression, or invocation. It runs only under `--clone-drift`, which is
opt-in on top of an already opt-in rule.

**Incomparable sets are capped at Advisory and carry a caveat.** The caveat is deliberate: the
finding is *not* dropped. A shape collision is still a one-sided change to a similarly-shaped region,
and hiding that would be hiding evidence. What is withdrawn is the assertion that the sibling is a
peer — "an equivalent change reached the sibling later" becomes "a change reached a similarly-shaped
region, and token-identity is the only evidence these are the same code".

**Reference monorepo, same flags both sides: 3,790 → 3,790.** SNP0032 High **6 → 5**, Advisory
189 → 190. Nothing added, nothing removed — tier and message only. `IOrderApi.cs` (the case
1.12.0 recorded as F6 territory) is demoted, and 38 findings now carry the caveat.

**Only one of the two cases 1.12.0 named is demoted, and the other is left deliberately.**
`UpdateCustomerRequest.cs` shares a set with `CustomerDetailsRequest.cs`, whose region includes a
method body, so the set is not declaration-only and the guard declines. That is the conjunction
behaving as designed: it will not demote on ambiguous ground. Narrowing it to reach that case would
mean demoting any set with a method anywhere in it, which is the over-broad version the measurement
already rejected.

**Snipper's own source: the change was scored by its own rules and fixed rather than baselined.**
Adding the conditional pushed `CollectFiles` to cognitive 17 and `CloneDriftDetector.Evaluate` to
40/16. Both were reduced by extracting the added logic into `EvidenceFor` and `ComparabilityCaveat`,
the same move 1.11.0 made. Self gate: **84 known, 0 new**, and the baseline drops from 83
fingerprints to 82 — one true positive removed rather than absorbed.

## What was deliberately not done

No refactoring of the methods 1.14.0 reports. Snipper is read-only by locked decision, and a release
that adds a complexity rule does not become a release that fixes complexity.

## Post-release: SNP0031 was naming absolute paths in its message

Found while auditing the backlog, not by the monorepo A/B — the finding count was always correct, so
nothing in the run-to-run comparison could surface it. `DescribeDuplicationPartners` had a doc
comment promising *"repository-relative `path:line`"* and emitted `location.Path` verbatim, which is
Roslyn's `document.FilePath`, i.e. absolute.

The severity is in where it lands. The baseline fingerprint is `RuleId | relativePath | Message`,
and `BaselineService` shortens `relativePath` — but the **message is hashed verbatim**. So naming an
absolute path in the message reintroduced through the message exactly the machine dependence that
shortening the path field exists to remove: a baseline recorded at `C:\build\repo` reports every
SNP0031 finding as new on `C:\Users\someone\repo`. The report also carried the analysing user's
directory layout to whoever read it, and the backslashes meant the same tree fingerprinted
differently on Windows and Linux.

SNP0032 already had this right — `CloneDriftDetector.ToRepositoryRelative` relativises and rewrites
separators — which is how the omission stood out: two rules reading the same clone sets, one
speaking the contract and one not.

Fixed by giving `DuplicateFragmentAnalyser` the same root `ComputeFingerprint` uses, passed down
from `CliRunner` so there is one definition rather than two that can drift. With no root supplied
the analyser derives the deepest directory containing every analysed file, so a caller who omits the
argument gets the portable spelling rather than the leaky one. Paths are written with forward slashes,
matching `ComputeFingerprint`.

**This changes the SNP0031 message, so it requires a re-baseline** — the same cost as 1.9.0, 1.10.0
and 1.13.0, all of which also touched this message. Four tests, all confirmed red before the fix:
no absolute root, forward slashes only, every named copy still resolves to a real file under the same
root, and the same contract holds with no root supplied.

**Reference monorepo, same flags both sides (`--duplicate-detection --clone-drift`): 3,790 →
3,790. SNP0031 1,131 → 1,131, SNP0032 195 → 195.** Every SNP0031 anchor is at the same path and
line, so no finding was added, removed or moved; 0 of 1,131 messages still contain a drive path;
and SNP0032 is byte-identical including its message, which is the control - it already relativised,
so a change there would have meant the two rules had been left disagreeing.
