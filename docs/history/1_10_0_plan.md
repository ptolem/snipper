# 1.10.0 — one location per file, and a copy count that means something

**Status:** implemented, measured, released.

## What was wrong

1.9.0 reported one finding per clone set, which was correct, but the *members* of each set were wrong.
A set could claim more copies than it had places.

`DuplicateFragmentAnalyser` skips matching a file against **itself**:

```csharp
if (string.Equals(left.Path, right.Path, StringComparison.Ordinal))
{
    // One copy per path by design (decision 5).
    continue;
}
```

That comment was wrong, and it was wrong in a way that survived every release from 1.0. The guard is on
**pairs**, not on **sets**. A–B is a legal pair. B–C is a legal pair. Union-find merges them, and the
set `{A, B, C}` now contains A twice. "One copy per path" was never enforced on the set that actually gets
reported.

Measured on the reference monorepo at 1.9.0:

| | |
|---|---|
| Sets listing a file more than once | 93 of 1,094 |
| Copies that were a 2nd-or-later fragment from a file already present | **1,210 of 4,379 (27.6%)** |
| Sets whose message contradicted itself | 93 |

Those extra fragments were not separate copies. They were **windows over one duplicated region, measured
at shifted token offsets**. The signature is unmistakable in the worst case:

```
70-token block (10 lines) duplicated 257 time(s) across 13 file(s).
```

`CTConstants.cs` alone contributed **85 locations** at lines 6, 8, 9, 10, 11 … 108. That is not 85 copies;
it is one constant table being re-detected as the window slid down the file. And the message contradicted
itself: "257 times across 13 files" is not a sentence that can be true.

Per-fragment reporting in 1.9.0 and earlier had hidden this — the numbers were large enough that nobody
added them up against the file list.

## The change

**Each file contributes one location per set.** Fragments from one file are merged into their enclosing
span — earliest start, furthest end — so the location covers the whole duplicated region rather than
whichever window happened to match first.

Merge semantics are chosen deliberately:

- **Adjacent or overlapping fragments merge.** They are the same region seen at shifted offsets.
- **Two disjoint regions in one file also merge**, because the file is where the duplication lives and
  there is one file-level answer to "where". The merged span is honest about covering both.
- Ordering is by `(path, start line, start character)`, so the anchor cannot move between runs.

Sets that collapse to a single file are dropped: one surviving location has no sibling to be duplicated
from, which is the same floor `CloneSet` already applies.

## Measured — interleaved A/B, same session, same target

| | 1.9.0 | 1.10.0 |
|---|---|---|
| Sets | 1,094 | 1,094 (unchanged) |
| Copies claimed | 4,379 | **3,169 (−27.6%)** |
| Sets listing a file twice | 93 | **0** |
| Self-contradicting messages | 93 | **0** |
| Every other rule | — | **byte-identical** |

The headline set:

```
before: 70-token block (10 lines) duplicated 257 time(s) across 13 file(s).
          85 locations in src\Metro60.Common\CTConstants.cs
          58 locations in src\Metro60.CMS.API\Model\Bloomreach\Constants.cs
after : 71-token block (13 lines) duplicated 28 time(s) across 28 file(s).
           1 location  in src\HelloWorld\Program.cs
           1 location  in src\Milkrun.Products.Exporter.Nash\Program.cs
```

257 phantom copies in 13 files becomes **28 real ones in 28 files**. `CTConstants.cs` goes from 85
locations to 1. Nothing was suppressed — a window that had been counted as a copy now reports as part of
the region it belongs to.

## Two bugs of my own, caught by measurement

Both were invisible to the unit tests and visible only in the aggregate.

**The message kept the pre-merge count.** The message was built from `reported.Count` while `fileCount`
came from the collapsed list, so after merging it read `duplicated 33 time(s) across 9 file(s)` with 9
locations — still self-contradicting, in 93 sets. Both numbers are now read from the same collapsed list
and are equal by construction. This is why the fix asserts `copies == files` rather than asserting a
count.

**A mis-measured A/B nearly became a conclusion.** An earlier comparison showed SNP0001, SNP0006 and
SNP0019 moving by −6/+3/+4 and sets going *up* by 2. That looked like a regression. It was target-repo
drift between sessions — the same MILKRUN effect documented in 1.7.5, and the same one that made a SARIF
count difference look like a serialization bug earlier in this session. Re-measured interleaved in a
single session: **every other rule identical.** The lesson is the reason the harness defaults to
interleaved runs, and the reason no conclusion here rests on a cross-session comparison.

## Documentation corrected

- `DuplicateFragmentAnalyser.cs` — the `decision 5` comment now states what the guard actually does and
  points at the collapse step.
- `README.md` / `usage.md` — `relatedLocations` reads one location per **file**; a set's copy count
  equals its file count.

## Migration

Same trade-off as 1.9.0 and for the same reason: the fingerprint covers the message, and both numbers in
it changed. **1.10.0 requires a re-baseline.** Note that 1.9.0 already forced one, so a consumer upgrading
across both does it once now rather than twice.

## Tests

Six new tests in `DuplicateFragmentAnalyserShould`:

- every finding lists each file at most once (end-to-end against the fixture)
- `copies == files` in every message, and both equal the location count
- merging shifted fragments of one file yields the enclosing span
- disjoint regions of one file merge into one covering span
- a single-file set is left alone
- collapsed ordering is deterministic, so the anchor cannot move between runs
