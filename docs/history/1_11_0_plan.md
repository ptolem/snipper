# 1.11.0 — wire-contract evidence (F2 + F3)

**Status:** implemented, measured, released.

## The backlog said one thing; there were four

F2 and F3 were filed together in 1.7.1 as *"a rule has no channel for evidence that only exists outside
the compiler's model"* — a single defect with one missing channel. Implementing them found **four**,
and only the first was the one the diagnosis named. That gap is the interesting result; the finding
counts are the boring part.

| # | Missing channel | Symptom | Found by |
|---|---|---|---|
| 1 | **Minimal-API typed results.** `MapGet(…, Handler)` where the handler returns `Ok<ResponseWrapper<T>>` — the return type *is* the wire shape | Response DTOs whose only route to the wire was a minimal-API handler read as zero-reference | Reading milkrun's `FavesRoutes.cs` |
| 2 | **Base types in the DTO closure.** The closure walked generic arguments and members, never `BaseType` | Seeding `ListingProduct` reached **none** of `ListingProductBase`'s 32 response properties | Finding that channel 1 alone moved SNP0018 by 4 findings, not 40 |
| 3 | **Enum ordinals.** An enum member's *number* travels in messages | `deleting a member renumbers every later one, and the next in-flight message decodes as a different command` | The maintainers had written it in the attribute text all along |
| 4 | **Extension holders.** `value.Method()` binds to the method, never to the class | A heavily-used obsolete holder reported unreferenced because its own name appears nowhere | SNP0006 already had the rescue; SNP0018 did not |

Channels 1 and 2 are shared: both feed one DTO closure, and both suppress SNP0005/SNP0006 *and* SNP0018.
That is why they shipped together, as the sequencing note said they would have to.

## SNP0018's last finding is a true positive

`M60.BridgingServices.Core/Extensions/CustomFieldsExtension.cs:5` — obsolete `GetFieldValue<T>`, one
call site in the repo, and no references. Both halves of that are true at once: there are **two**
identical obsolete `GetFieldValue<T>` extensions, one in `M60.BridgingServices.Core` and a twin in
`Metro60.Common.CommerceTools`, and the surviving call binds to the twin. The copy with no callers is
genuinely dead. Left as reported.

## Enum ordinals: what was suppressed and what was only re-tiered

Suppressing every `[Obsolete]` enum member would have been easy and wrong — it removes the signal
without a reason. The rule shipped as:

- **Ordinal-bound enum** (type argument of a `JsonConverter`-derived type, or of `Enum.GetValues<T>()`)
  → **suppressed.** The removal advice is actively wrong: the next message carrying that ordinal
  silently dispatches to a different case.
- **Any other enum member** → **still reported, down-tiered to Advisory**, with the hazard in the
  message: *"Removing it renumbers every later member of 'X', so any ordinal already on the wire will
  then resolve to a different member — retire it by renaming or leaving a placeholder instead of
  deleting."*

`Dictionary<UnboundCommandType, string>` is deliberately **not** treated as an ordinal contract. An enum
as a generic key is a lookup, not a wire binding; conflating the two would have suppressed on a much
wider surface for no gain. The fixture pins both directions.

## What the investigation got wrong

1.7.1 sized F2 at "49 of 70 SNP0006 findings, 70%". At 1.11.0 the rule reported **1,647**, and the
wire-contract share was **89 — 5.4%**. The 70% was measured when the rule was far smaller and before
1.5.0's framework-evidence work reshaped it. The class was real; the number attached to it was six
years of drift out of date. Any backlog figure should be re-measured before it is used to size work.

## A latent bug the work exposed

`AddressResponseModel` was in the DTO closure — verified by instrumenting the closure — and its obsolete
property was still being reported. The reason: **symbol equality is not transitive across compilations
of the same project.** A loaded solution can hold two distinct `Compilation` objects for one project,
each with its own `INamedTypeSymbol` for the same source type. A seed resolved from a dependent
project's semantic model then fails a `SymbolEqualityComparer` lookup against a candidate resolved from
the defining project's own model. Milkrun's closure contained **127 types twice under identical display
names**, which is how it was found.

The fix keys the closure additionally by fully-qualified definition name, consulted only on a symbol
lookup miss, so the common same-compilation case stays a hash lookup with no string built. This was
worth ~98 of the 140 suppressions — without it the channels were largely inert on a solution that is
merely *large*, which is the common case.

## Tests

`+20` (616 → **636**), on a new `WebLib` fixture project carrying a `Microsoft.AspNetCore.App`
framework reference. Every channel has a **negative control**, because a suppression test with no
counter-test proves only that the rule stopped talking:

- `OrphanPayload` — obsolete property on a type no route or serializer returns → **must still fire**.
- `FakeRouter.MapGet` — an application-defined method with a route-shaped name → the semantic gate must
  reject it, so `FakeRouterResponse.PlainUnreferenced` stays reportable.
- `UnboundCommandType` — an enum with no ordinal contract → **still fires**, at Advisory.
- `DeadLegacyStringExtensions` — an obsolete holder with no called method → **still fires**.
- `Dictionary<UnboundCommandType, string>` — a generic key is not a converter → the enum stays reportable.

Two of these fixtures were wrong on first run and the tests caught both. The `FakeRouter` control
referenced its own target property, and an assertion using `Contains("LegacyStringExtensions")` also
matched `DeadLegacyStringExtensions`. The assertions now quote the symbol name.

## Self-analysis

The refactor that introduced the evidence gate pushed `EvaluateCandidateAsync` to cyclomatic complexity
22, and **SNP0033 said so on Snipper's own source**. That was a true positive, so it was fixed rather
than baselined: the gate is now one call, with `CertaintyFor` / `MessageFor` / `FindObsoleteAttribute`
extracted. Back under threshold.

One SNP0011 remains new, for `WebLib.csproj` — a fixture project deliberately not in `Snipper.slnx`, like
its six siblings. It is recorded in the baseline rather than fixed here: the rule's treatment of
test-asset projects is F6-class work, not a change to smuggle into this release.

## Migration

Same trade-off as 1.9.0 and 1.10.0: the fingerprint covers the message, and 48 messages changed.
**1.11.0 requires a re-baseline.** A consumer upgrading across 1.9–1.11 re-baselines once, at 1.11.
